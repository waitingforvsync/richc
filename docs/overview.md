# richc reference

richc is a single C17 helper library that replaces the C standard library for
console and windowed applications, in two layers: a dependency-free **core**
(data structures, algorithms, math, strings, I/O) and an **app** layer
(windowing, input, image loading, packing, and atlasing) built on top. This page
covers the philosophy and conventions shared by both; the per-header reference is
split into [core.md](core.md) and [app.md](app.md).

## Philosophy

richc favours high performance built from a small, predictable set of
primitives. A handful of principles run through the whole library; once they are
clear, most of the API follows from them.

**Arena allocation is the only allocation.** The library never calls `malloc`,
`realloc`, or `free`. Every allocating operation takes an `rc_arena *` - a
virtual-memory-backed bump allocator that reserves a large address range up front
and commits pages on demand - named `arena`, as its last parameter. Allocation is
a pointer bump (fast and cache-friendly), and lifetimes are explicit: you free an
arena, not individual objects. Allocation never returns NULL; running out of
space is a panic, not an error to handle, so arena results are never NULL-checked.
(Arena *creation* can fail - check `rc_arena_make`'s result.) The `arena` argument
may be NULL when a call provably needs no allocation.

**Scratch arenas are passed by value.** Passing an `rc_arena` *by value* hands the
callee a snapshot of the bump pointer. Allocations inside the callee advance only
that copy, so on return the caller's arena is unchanged and the temporary memory
is reclaimed for free, with no explicit cleanup. A function that needs working
memory takes a second arena by value for scratch.

**Give a growable container its own arena, or let it grow last.** `rc_arena_realloc`
grows the *latest* allocation in place - same address, thanks to the reserved
range - so a growable array that is its arena's most recent allocation never
moves, and raw pointers into it survive growth. A block that is no longer the
latest is relocated by copy when it grows, invalidating pointers into it. So keep
one growable per arena, or make the growable the last thing allocated; otherwise
hold stable indices rather than pointers across a growth.

**Spans and views are the fundamental sequence types - prefer them to a raw
pointer and length.** A `rc_view` is a read-only `{const T *data; uint32_t num}`,
a `rc_span` its mutable counterpart `{T *data; uint32_t num}`, and a `rc_array`
adds a capacity over arena-backed storage it owns. They share an anonymous union,
so an array converts to a span or a view, and a span to a view, as a typesafe
field access with no function call. Pass a span or a view anywhere you would
otherwise pass a pointer-and-count pair: it keeps the two together, carries
const-ness in the type, and plugs straight into every algorithm.

**Prefer indices to pointers.** An index into a container stays valid across
growth and relocation where a raw pointer may not, and it is half the size. The
index type is `uint32_t`, with `RC_INDEX_NONE` (`UINT32_MAX`) as the "not found"
/ "invalid" sentinel. APIs return and accept indices in preference to pointers
wherever it makes sense - the object pool hands out stable indices, the search
algorithms return indices.

**Return by value; reserve out-parameters for real need.** Functions return their
result - often bundled into a small struct - rather than writing through an
out-parameter. Returning by value keeps data in registers, avoids forcing it to
memory through a pointer, and reads more clearly. An out-parameter is used only
when the alternative is genuinely worse: filling a caller-owned buffer, or
returning a large object that should not be copied.

**Containers and algorithms are compile-time templates.** Generic types are
generated by the preprocessor: define a control macro, include a
`richc/template/` header, and it emits type-specific code, then `#undef`s its
macros so it can be included again for another type. There is no runtime
polymorphism and no `void *` - the generated code is as specific, and as
optimisable, as if it were written by hand.

**Preconditions trap; errors are only for what a caller can handle.** A
precondition a function relies on but does not itself handle - a non-NULL pointer,
an in-range index, a well-formed value - is guarded by `RC_ASSERT` (active in
debug builds) and traps on violation. `RC_PANIC` is for unrecoverable runtime
failures that must abort even in release (such as an arena exhausting its
reservation). A returned error result is reserved for conditions a caller is
genuinely expected to handle, like a file that fails to open.

## Conventions

- All public types and functions are prefixed `rc_`; all public macros `RC_`.
  Everything is `snake_case`.
- Function naming by role:
  - `rc_<type>_make(...)` / `rc_<type>_make_<thing>(...)` acts like a
    constructor - it returns a fresh `rc_<type>` by value.
  - `rc_<type>_from_<other>(...)` acts like a conversion constructor - it builds
    an `rc_<type>` from a value of a different type.
  - `rc_<type>_as_<other>(...)` acts like a cast - it reinterprets the value as
    another type without allocating or copying, leaving the source usable.
  - `rc_<type>_to_<other>(...)` converts into another type by *moving* - it
    consumes the source (resetting `*src`) so only the result owns the resource
    (e.g. `rc_array_bytes_to_mstr`).
  - `rc_<type>_is_<predicate>(...)` returns a `bool` (e.g. `is_valid`,
    `is_empty`).
- A trailing underscore denotes an internal (private) symbol that happens to be
  visible in a public header (e.g. `RC_CHECK_IMPL_`, a generated `_grow_`
  helper). Do not use these directly; they are not part of the API.
